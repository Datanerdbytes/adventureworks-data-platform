# Performance audit: verification against source

Reviewed 2026-10-15 against branch `integration`, commit
`7020dd0e0c774697ba2e5f3c78e9417c28d64537`, and the working copy of
`PERFORMANCE_AUDIT.md`. The original audit already had staged and unstaged edits;
this review preserves it. Application performance changes have not been made.

This is a source review and offline verification, not a production benchmark.
“True” establishes the described behavior, not a measured latency, cost, or
capacity problem. “Unproven” means measurements are needed before remediation.

## Additional confirmed observations

- **A01 — Very small cache capacity:** `init_kpi_cache` sets `CACHE_THRESHOLD=10`.
  `tests/test_cache_coverage.py` inventories 21 memoized loaders, before filter
  combinations and memoization metadata. Installed CacheLib's
  `FileSystemCache._prune()` removes expired entries and then older entries when
  over threshold, including still-live entries. This is an eviction-pressure
  risk independent of TTL. Actual production eviction/hit rates remain unknown.
  Existing coverage tests use a threshold of 500 and therefore do not exercise
  the production capacity setting.
- **A02 — Cleanup gap:** the migration should close its BigQuery client and
  dispose its PostgreSQL engine on success and failure, including when the
  second resource fails to initialize. This concerns CLI lifecycle, not evidence
  of a dashboard pool leak.

Warming arbitrary filter combinations can waste warehouse work.                                                                                                  |

Improve CLI cleanup; tune pool capacity only with a demonstrated connection budget.                                                                                                                          |

Profile actual SQL before changing history/fallback semantics.                                                                                                                                                                  |
| Add governance timeout                                          | Already implemented. Do not duplicate it or claim it as new remediation.                                                                                                                                                                                       |
| Move cache to Redis to eliminate stampedes                      | Incorrect guarantee. Shared storage alone does not coalesce concurrent cache misses. Distributed coordination and deployment topology need a separate design if multiple instances require it. Do not reuse authentication Redis implicitly.                   |
| Chunk ELT and upload incrementally                              | Accept bounded extraction, but reject naive repeated WRITE_TRUNCATE or direct truncate-then-append publication. The former loses earlier chunks; the latter exposes partial results after a failure. Use bounded staging with a single final replacement load. |

## Evidence and verification limits

Source anchors include `docs/cache-coverage.md`, `Dockerfile`, the 21-loader
inventory in `tests/test_cache_coverage.py`, and the current implementations
identified above. Sequential cache coverage does not establish concurrent
single-flight behavior. Mocked warehouse responses do not establish query speed.

External references checked on the review date:

- [SQLAlchemy connection pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html)
  confirms default pooling; explicit pool sizing is optional configuration.
- [BigQuery compute optimization](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-compute)
  explains that repeated CTE evaluation depends on optimizer decisions.
- [BigQuery query plans](https://docs.cloud.google.com/bigquery/docs/query-plan-explanation)
  describes the execution evidence needed to assess stages and resource use.

The executable handoff is [PERFORMANCE_IMPLEMENTATION_PLAN.md](PERFORMANCE_IMPLEMENTATION_PLAN.md).

Baseline verification on 2026-10-15: the safe Python runner passed **210 tests**
in 3.369 seconds using a temporary writable `UV_CACHE_DIR`. The default uv cache
was sandbox-blocked; the temporary-cache retry succeeded. Both new documents
were formatted with the repository's installed Prettier. No live services or
application code changes were involved.
